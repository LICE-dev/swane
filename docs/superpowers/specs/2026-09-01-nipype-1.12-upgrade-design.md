# Nipype 1.12 upgrade — design

Date: 2026-09-01
Branch: `claude/nipype-1.12` (rebased from `enh-nipype-1.12` onto `dev`)

## Goal

Bump SWANe's pinned Nipype from 1.10.0 to 1.12.0 and remove the local code that
has since landed upstream in Nipype, restoring the native interfaces where SWANe
previously carried subclasses/workarounds. Verify the runtime monkeypatches
still target valid surface, update the affected tests, and add the
"derived from Nipype" disclaimer to the RAM estimators now that they extend a
Nipype class.

This is a software-maintenance change. It is regression-tested only; a passing
suite is not scientific or clinical validation.

### CustomEddy vs native Eddy — native is insufficient, keep CustomEddy

Confirmed against the real FSL 6.0.7.22 on this box: `eddy_openmp` **does not
exist**; the binaries are `eddy` (auto-selects GPU when CUDA is present, else CPU),
`eddy_cpu` (forces CPU), and `eddy_cuda`. On newer FSL `eddy_cuda` is also gone.

Native `Eddy._use_cuda` is `self._cmd = "eddy_cuda" if use_cuda else "eddy_openmp"`;
`_run_interface` only falls back `eddy_openmp → eddy` via `$FSLDIR/bin`. On modern
FSL this is broken for SWANe's needs:

- `use_cuda=False` (user explicitly wants CPU) → native tries `eddy_openmp`
  (missing) → falls back to `eddy`, which on an NVIDIA box **runs on the GPU** —
  contradicting the user's choice. The correct binary is `eddy_cpu`.
- `use_cuda=True` → native uses the literal `eddy_cuda`; on newer FSL that binary
  **does not exist** and there is no fallback in the cuda path → command not found.

`CustomEddy` implements exactly the semantics FSL requires: `use_cuda=False →
eddy_cpu` (forces CPU, via `which`), `use_cuda=True → eddy_cuda` or, if absent,
`eddy` (auto-GPU); it also sets `num_threads = 1` under CUDA. `CustomEddy` is a
SWANe customization for FSL binary naming, **not** upstreamed code, so it is kept.

Because `CustomEddy` already forces `num_threads = 1` under CUDA, the previously
considered "add a workflow line for num_threads" is unnecessary — keeping
`CustomEddy` preserves that behavior for free.

### Nodes that stay

- `CustomEddy` stays (see above). The draft commit `a9bb80d` switched
  `dti_preproc_workflow` to native `Eddy`; that switch is reverted back to
  `CustomEddy` (dev and the merge-base both use `CustomEddy`).
- `CustomDcm2niix` stays: it keeps SWANe-specific `expected_files` / `request_dti`
  traits and the post-run validation in `_run_interface`. Only its `name_conflicts`
  trait (now native) is removed — already done in the draft.

## Contracts touched

- Packaging: `setup.py` `install_requires` (nipype pin, filelock removal).
- Nodes: deletion of `CustomProbTrackX2` (already unused). `CustomEddy` kept.
- Workflow: `dti_preproc` reverts to `CustomEddy` (restores correct FSL binary
  selection: `eddy_cpu` for CPU, `eddy_cuda`/`eddy` for GPU).
- Disclaimers: `ram_estimators.py` gains derived-code notice (licensing hygiene).
- Matrix snapshot golden files (test contract) — regenerated.

## Out of scope

- No change to `CustomDcm2niix` beyond the already-removed `name_conflicts`.
- No scientific re-validation / oracle runs.
- No change to the `cuda` preference gating.

## Risks

- Rebase conflicts against dev's tractography-refspace work — mitigated by the
  draft being a single, fully-understood commit.
- A monkeypatch that silently no-ops under 1.12 (assert on real file location, not
  just "no exception").
- Installing nipype 1.12 may shift a transitive pin (networkx/traits) — inspect
  after install; a conflicting pin fails loudly, a compatible bump needs a look.
