### Heavy suite run — 2026-09-01

Ran on this box (no CUDA, no FreeSurfer): `pytest -p no:datalad --run-heavy swane/tests/nipype_pipeline/nodes swane/tests/helpers swane/tests/workers`.

Result: **272 passed, 3 skipped, 0 unexplained failures** (after the two fixes below).
Skips are all `fsaverage`/FreeSurfer-gated phantom tests — expected on this box.

Two issues found and fixed. Both files are untouched by this branch and already exist on
`dev` — neither is a nipype 1.12 regression, just latent bugs never exercised by heavy
tests on this box before:

1. **Real bug, fixed in production code** — [`AntsN4BiasFieldCorrection.py`](../../../swane/nipype_pipeline/nodes/AntsN4BiasFieldCorrection.py): the `skull_stripped`/`mask_file` branches built the mask via a boolean comparison (`img > 0` / `mask > 0`), which antspyx types as `unsigned char`. Isolated experimentally: `ants.n4_bias_field_correction` (antspyx 0.6.3) corrects much more weakly with an `unsigned char` mask than a `float` mask holding the identical 0/1 values (corrected std stayed ≈ biased std instead of dropping). Fixed by `.clone("float")` on both branches; the Otsu-fallback branch was already float and unaffected. `test_reduces_a_synthetic_bias_field` now passes.
2. **Flaky test, fixed in the test only** — `test_ants_apply_transforms.py::test_inverse_round_trip_recovers_the_moving_image`: `AntsRegistration`'s affine stage samples points randomly each iteration with no seed input exposed on the node, so the real round-trip correlation flipped pass/fail run to run (this supersedes the "one flaky real-ANTs correlation test" non-regression noted in Global Constraints — it is now fixed, not just tolerated). Fixed by pinning `ants.config.set_ants_deterministic(True, seed_value=123)` for the test's duration only, restored in a `finally`. Confirmed deterministic and green across 3 isolated reruns; no change to `AntsRegistration` itself.

Open, not investigated (out of scope for this pass, flagged for the orchestrator):
- `TestSlicerCheckWorkerReal::test_slicer_detection_and_module_lifecycle` — one run reported `DETECTED` right after the "simulated absence" file move (expected `MISSING`), and an isolated rerun exceeded 2 minutes. Real Slicer install integrity was verified intact both times (the test's `try/finally` restore held). Not caused by this branch (file untouched, pre-existing on `dev`); likely I/O contention on this resource-constrained box after a long heavy run, not root-caused.
